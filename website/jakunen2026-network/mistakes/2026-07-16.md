# 2026-07-16

## グループ共有ディレクトリにsetgidビットがないとグループクォータが機能しない
- 症状: RAID・samba共有・グループクォータの上限設定まで全て正しく見えるのに、g_smb所属ユーザーが書き込んでも`repquota -g`の使用量が全く増えない
- 原因: `/var/samba`に`setgid`ビット(`g+s`)が立っていなかったため、ユーザーが作成したファイルは**そのユーザー自身のプライマリグループ**のまま所有され、`g_smb`グループの所有にならなかった。グループクォータはファイルの所有グループで集計されるため、無関係なグループのファイルはカウントされない
- 教訓: グループ共有ディレクトリは`chmod g+s`（または`chmod 2770`のように先頭に`2`を付ける）を必ず設定する。**「設定が完了したように見える」ことと「実際に機能すること」は別物**なので、quota系の課題では必ず実際にテストユーザーで書き込んでから`repquota`で確認する
- `chmod 2770`の`2`は特殊権限ビット（4=setuid, 2=setgid, 1=sticky）、`770`が`rwxrwx---`

## fstab編集後の再マウント忘れ（再掲・別パターン）
- `mount -a`は「未マウントのfstabエントリ」のみ対象。既にマウント済みのファイルシステムのオプション変更を反映させるには`mount -o remount <マウントポイント>`または`umount`→`mount -a`が必要
- `quotacheck`（オプションなし）はデフォルトでuser/group両方をチェックしようとするため、`usrquota`を設定していない環境では`-g`を明示しないと失敗する（`quotacheck -cvg <マウントポイント>`）

## SSH鍵認証: `~/.ssh`をsudoで操作するとroot所有になり認証できなくなる
- 症状: 公開鍵の中身・パーミッション(`700`/`600`)は正しいのに、鍵認証が通らずパスワード認証にフォールバックする
- 原因: `sudo mv`等で`~/.ssh`や`authorized_keys`を操作すると所有者が`root`になり、対象ユーザー自身がそのディレクトリに入れなくなる。sshd側も`Could not open user '<user>' authorized keys ... Permission denied`（`journalctl -u ssh`で確認可能）としてファイルを読めない
- 教訓: `~/.ssh`関連の操作はそのユーザー自身の権限で行う（sudoを挟まない）。sudoを使ってしまった場合は`chown <user>:<user> ~/.ssh ~/.ssh/authorized_keys`で必ず所有者を戻す

## SSH鍵認証: クライアント側の秘密鍵パーミッションも要注意
- 症状: `ssh -i id_rsa ...`で"UNPROTECTED PRIVATE KEY FILE"警告が出て鍵が無視され、パスワード認証にフォールバックする
- 原因: 秘密鍵ファイルのパーミッションが`0644`など緩い状態だった（Windows機からLinux機へファイルをコピーした際に権限が変わることがある）
- 教訓: `chmod 600 <秘密鍵ファイル>`をクライアント側でも忘れずに。サーバ側だけでなくクライアント側の鍵パーミッションも認証失敗の原因になりうる

## その他SSH関連の注意点
- 公開鍵をサーバに登録する際、ファイル名を`id_rsa.pub`のまま置いても認証されない。sshdが読むのは`~/.ssh/authorized_keys`という決まったファイル名のみ
- `/etc/hosts.allow`・`/etc/hosts.deny`（TCP Wrappers）はDebian 9以降のopenssh-serverでは機能しない。ネットワーク制限は`sshd_config`の`AllowUsers user@CIDR`かiptablesで行う
- `AllowUsers`は要件が「特定ネットワークからの接続制限」のみでユーザー指定がない場合、`*@<CIDR>`（全ユーザー対象）の方が要件に忠実（余計な制限を課さない）
