# 2026-07-27: TCP接続不通・ACL順序・IPv6 ND関連

## GNS3 Cloudノード経由でLinux VM(virtio)→dynamipsルータへの新規TCP接続が全滅する
- 症状: ICMP(ping)・UDP(DNS等)は正常なのに、**新規TCP接続だけが毎回SYN送信のまま応答なしでタイムアウト**する。NAT変換・ACL・ARP・ルーティングは全て正常に見える
- 原因: virtio NICのTCPチェックサム/セグメンテーションオフロード。GNS3のCloudノードはraw socketでフレームをそのままdynamipsルータへ橋渡しするため、まだ計算されていない(オフロード予定の)チェックサムがそのまま渡り、ルータ側で不正パケットとして扱われる
- 切り分け方: ルータ同士(dynamips↔dynamips)のTCPは正常なのに、ルータ↔Linux VM(同一サブネット、NAT無し)のTCPだけ失敗する場合はこれを疑う。`/proc/net/dev`でTCPテスト前後のRX/TXカウンタを比較し、「相手には届いているのに応答が一切送信されていない」ことを確認するのが決め手
- 対処: ホスト側tapのethtool設定変更は**効果なし**(ゲストの仮想NIC機能はブート時にネゴシエーション済みのため、後から`ethtool -K tapXXX tx off ...`しても反映されない)。hookscriptで起動直後に適用しても同様に効果なし
- **正しい対処**: PVEの`qm set <vmid> --net0 e1000=<mac>,bridge=<bridge>`でNICモデルをvirtioからe1000に変更し再起動する。IPアドレス設定(ens18等のインタフェース名)は維持される。osv1/osv2/osv3で実施し解消を確認済み
- 教訓: この構成(GNS3+PVE+Cloudノード+Linux VM)を使う限り、今後作成するVM(tsv/ksv/sv含む)も同じ問題を抱える可能性がある。TCPサービスの疎通が原因不明で失敗する場合は、まずNIC modelを疑う

## NAT+ACLの順序: 外側インタフェースのinbound ACLはNAT変換前のグローバルアドレスで書く
- 症状: 静的NAT・動的PATの設定自体は正しいのに、外部からNAT変換後アドレスへのping/TCP/DNSが全て届かない
- 原因: `ip access-group ACL_NAME in`を外側(outside)インタフェースに適用した場合、ACLは**NAT変換が行われる前**の状態でパケットを評価する。つまり外部から届いた時点のパケットの宛先は、まだ**変換前のグローバル(公開)アドレス**であり、変換後のローカル(内部)アドレスではない
- 具体例: `ip nat inside source static 10.100.0.1 201.10.0.3`と設定していても、ACLに`permit tcp any host 10.100.0.1 eq www`と書いてしまうと、実際に届くパケットの宛先は`201.10.0.3`なので一致せず、暗黙denyで弾かれる。正しくは`permit tcp any host 201.10.0.3 eq www`
- 動的PAT(overload)でも同様。戻りパケット(ICMP echo-reply、TCP established)の宛先はPATプールのグローバルアドレス(例: `201.10.0.4`)であり、内部クライアントの実アドレスではない
- 切り分け方: ACLで許可しているはずの通信が0%失敗する場合、`show ip nat translations`で変換自体が生成されているか確認する。生成されているのに通らなければACLのアドレス指定を疑う
- 教訓: 「外側インタフェースのinbound ACLに書くアドレスは、常にNAT変換後(グローバル)のアドレス」と覚える

## `established`キーワードはTCP専用、ICMP/UDPには使えない
- `permit ip any host X established`・`permit icmp any host X established`はいずれも`% Invalid input` / `% Unrecognized command`でエラーになる
- ICMPの戻り(pingの応答)だけを許可したい場合は`permit icmp any host X echo-reply`のように具体的なメッセージタイプを指定する必要がある
- UDPには戻りだけを区別する仕組みがACL単体には存在しない(コネクションレスでフラグを持たないため)。「発信したUDPの戻りだけ許可」は素の拡張ACLでは原理的に不可能(CBAC/reflexive ACLが必要、この演習レベルでは想定外と判断)

## IPv6 ACL: 明示的な`deny ipv6 any any`はICMPv6 ND(近隣探索)まで巻き込んで塞ぐ
- 症状: ACLの各許可行(DNS/Web/echo等)は正しいのに、**外側インタフェースを挟んだ隣接ルータとの通信が(許可されているはずのechoも含めて)全く成立しない**。`show ipv6 neighbors`が空のまま
- 原因: Cisco IOSのIPv6 ACLは、ICMPv6の近隣要請/近隣広告(NS/NA、ARPに相当)を**自動的に暗黙許可**する仕様があるが、これは「設定した全ての行の後、本当の暗黙deny(all)の直前」に挿入される。ところが**自分で明示的に`deny ipv6 any any`を書くと、この自動許可より先にそちらが評価されてしまい、ND自体がブロックされる**
- これによりNDが解決できず、直結ルータ同士ですら永久にpingが通らない(ARPが引けないのと同じ状態)
- 対処: `deny ipv6 any any`より前のシーケンス番号で`permit icmp any any nd-ns`・`permit icmp any any nd-na`を明示的に追加する
- 教訓: IPv4のACLと違い、IPv6 ACLで明示的な`deny`を書く場合は、ND用の許可行を必ずセットで入れる。「ACLの中身は合っているのに何も通らない」という時はまずNDを疑う

## 誤診断: PCIバス帯域超過を疑って大きく時間を浪費した
- ISP↔R-Kgw1間のIPv6が通らない件で、以前の教訓(c7200のPCIバス帯域超過で不安定化)を思い出し、ISPルータのスロット構成を疑って再起動・スロット変更(API/GUI共に不可と判明)まで試したが、**実際の原因は上記のIPv6 ACLのND問題だった**
- 同じPCIバス上の別インタフェース(Gi0/0)は正常に動いていた点(IPv4のARPはACLの影響を受けないため)を見落としていた
- 教訓: 「以前遭遇した既知の問題」に飛びつく前に、まず対象の設定(特にACLの中身)を一から丁寧に確認する。今回はIPv4とIPv6でARP/NDの扱われ方が違う、という基本に立ち返れば早期に気づけた

- 名前付きACLを`ip access-list extended NAME`で再度開いて`permit`を追記すると、既存の行の**後ろに追記される**(置き換わらない)。古い誤った行を消してから追記するか、`no ip access-list extended NAME`で一度全消去してから作り直す。既存の`deny`より後ろに新しい`permit`を追加すると、その`deny`が先に評価されて新しい行が永久に無効になる点に注意
