# 2026-07-08

## NSレコードの値にIPアドレスを直接書いた

**誤り**:
```
ns1	IN	NS	172.16.100.11
ns2	IN	NS	172.16.100.12
```

**正解**:
```
@	IN	NS	ns1.osaka-skills.jp.
@	IN	NS	ns2.osaka-skills.jp.
ns1	IN	A	172.16.100.11
ns2	IN	A	172.16.100.12
```

NSレコードの値はホスト名でなければならない。IPアドレスを直接指定すると`named-checkzone`で「NS record 'x.x.x.x' appears to be an address」「has no NS records」エラーになりゾーンが読み込まれない。owner名も`@`（ゾーン自身）にする必要があり、`ns1`/`ns2`という名前に付けると別のサブドメインへの委任として扱われてしまう。

## view の順序ミス（externalが先）

**誤り**:
```
view "external" {
	match-clients { any; };
	...
};
view "internal" {
	match-clients { 172.16.100.0/24; };
	...
};
```

**原則**: match-clientsは上から順に評価される。`any`は無条件マッチなので、限定的な条件（internal等）より後に書かないと、internalクライアントもexternalにマッチしてしまい内部viewが機能しない。

## osv1にnginxがインストールされたままでapache2とポート80競合

**状況**: osv1はapache2専用のはずだが、過去のnginxインストール操作の残骸が残っており、systemdがnginxを起動しようとしてapache2とport 80が競合、crashループしていた。

**対応**: `systemctl stop nginx; systemctl disable nginx` で解消。役割分担（osv1=apache2、osv2=nginx）を毎回確認すること。

## mod_userdirで403 Forbidden

**状況**: `/home/alice/public_html`のパーミッションは正しく設定したが、`/home/alice`自体が`drwx------`のままで、apacheの実行ユーザー(www-data)がホームディレクトリを通過できず403になった。

**原則**: mod_userdirを使う場合、`public_html`だけでなく親のホームディレクトリにも`o+x`が必要。

## squid経由アクセスで502 Bad Gateway（resolv.confの向き先ミス）

**状況**: squid設定自体は正しかったが、osv2の`/etc/resolv.conf`が`nameserver 8.8.8.8`のままで内部ゾーン(osaka-skills.jp)が引けず502 Bad Gatewayになった。`127.0.0.1`に変更しても`REFUSED`になった。

**原因**: bind9のview設定が`match-clients { 172.16.100.0/24; };`のため、送信元`127.0.0.1`はこの範囲にマッチせずview自体が選ばれなかった。

**正解**: `nameserver 172.16.100.12`（自分自身の実IP）を指定する。loopbackではなく実IPでなければview条件にマッチしない。

## squid.conf変更後、再起動しないと反映されない

**状況**: `/etc/resolv.conf`を修正した後もsquidが古いDNSサーバ(8.8.8.8)を使い続けていた。

**原因**: squidは起動時に`/etc/resolv.conf`を読み込んでキャッシュし、動作中は再読み込みしない。`cache.log`の`Adding nameserver`行で確認できる。

**対応**: resolv.conf変更後は`systemctl restart squid`が必須（`reload`では不可）。

## http_accessの順序ミス（allow→denyの順で書いてしまい、denyが評価されない）（反復練習1回目）

**誤り**:
```
http_access allow mynet
http_access deny block_site
```

**状況**: `172.16.100.0/24`から`test-block.jp`（フィルタ対象）にアクセスすると、送信元IPが先の`allow mynet`にマッチして即座に許可が確定し、後続の`deny block_site`が評価されなかった。結果、フィルタが効かず素通りし、squidが実際に接続を試みて`502 Bad Gateway`になった（`403`にならないので気づきやすい）。

**正解**: `deny`を`allow`より先に書く。
```
http_access deny block_site
http_access allow mynet
```

**教訓**: `http_access`は上から順に評価され最初のマッチで確定する。フィルタ系(deny)は必ず許可系(allow)より前に置く。順序ミスの症状は「403にならず502になる」（＝ブロックされずに素通りして接続失敗）なので、502が出たら順序を疑う。

## url_regexフィルタ追加時にhttp_access allow mynetを書き忘れる（反復練習2回目）

**状況**: `acl game_url url_regex -i game` と `http_access deny game_url` は正しく追加したが、対応する`http_access allow mynet`を書き忘れた。`acl mynet`自体は定義されているだけで、http_accessでallowされていなければ何の効果もない。

**症状**: `game`を含まない正規のドメイン(`in-www.osaka-skills.jp`)へのアクセスまで`403 Forbidden`になった。deny行にマッチしなかった通常リクエストが、`http_access allow mynet`が無いため最後の`http_access deny all`に落ちて拒否されていた。

**教訓**: 新しいdenyルールを1本追加するときは、既存のallowルール一式がまだ揃っているか毎回確認する。「フィルタを追加する」＝「denyを足すだけ」ではなく、その後段のallowが欠けていないかもセットで見る。想定外に全部が403になったら、まず`http_access allow`の行が抜けていないか疑う。
